## ① Subject 중복 — 어제 고친 게 또 터졌다. 다른 자리에서.

어제(9/24) 264행 앞에 `del msg['Subject']`를 넣어 고쳤다. 오늘은 **#37 일련번호
패치가 또 다른 지점**에서 제목을 한 번 더 얹었다. **증상은 같고 발생 지점은 다르다.**

★★★★★ **이건 패치를 하나 더 붙일 문제가 아니다 — `msg['Subject']`를 쓰는 자리가
코드 안에 여러 곳 있다는 뜻이다.** 어제처럼 그 자리 하나씩 막으면, 다음에 또
다른 패치가 세 번째 자리를 만든다. **`E-852`(main)가 이미 이 모양을 풀었다 —
"입력이 많으면 또 뚫린다, 답은 분할·단일화"**.

**처방: `msg['Subject']`를 함수 하나로 모은다.** 제목을 만드는 로직(기본 제목 +
일련번호 붙이기 등)은 여러 곳에서 각자 붙이지 말고, **메일 객체를 만드는 마지막
순간에 딱 한 번, 한 함수가 최종 제목 문자열을 조립해서 넣는다.** 그러면 다음에
새 패치가 "제목에 뭘 더 붙이자"고 해도 **그 함수의 입력에 항목을 하나 더할 뿐,
`msg['Subject'] = ...` 줄을 새로 안 만든다.**

## ② 둘째 출구(텔레그램)가 조용히 죽었다 — 감시가 감시 대상 안에 있었다

스크립트가 `no_agent` 크론으로 돌다 `_tg_alert` 코드에 닿기 전에 죽어서, **실패를
알리는 장치 자체가 실패와 같이 죽었다.** 이건 `E-215`·`E-249`·`quant/05`(main,
"감시가 감시 대상 안에 있었다")와 정확히 같은 모양이다 — **알림이 본체와 같은
프로세스 안에 있으면 본체가 죽을 때 알림도 같이 죽는다.**

**처방: 알림을 스크립트의 가장 바깥 예외 처리기로 옮긴다.**

```
try:
    (지금 하는 모든 일 — 메일 조립·발송·기록)
except Exception as e:
    _tg_alert(f"실패: {e}")   ← 이 줄이 파일 맨 위, 가장 바깥에 있어야 한다
    raise
```

**어디서 죽든 이 except 가 마지막으로 잡는다.** 지금처럼 `_tg_alert` 호출이 정상
흐름 중간에 있으면, 그 줄에 닿기 전에 죽는 모든 경우가 침묵한다. `E-925`(main)의
증거가 이미 같은 말을 했다 — *"밖으로 나간 행동은 감사 기록에 없다."* 알림도
같은 원칙이다 — **알림 코드가 실행되지 않으면 알림은 없는 것과 같다.**

## ③ ★★★★★ 수동 재실행이 실제 발송이 된 것 — 오늘 #41 원칙이 바로 이 자리에 쓰인다

**이게 가장 중요하다.** 뭉클이는 이 잘못을 "발송 전에 dry-run을 확인했어야 했다"고
적었다 — **주의를 안 기울인 것을 탓했다.** 그런데 오늘 아침 블록 #41 이 이미
답을 냈다: **"구조가 막아야지, 주의로 막으면 안 된다."**

★★★★★ **주의는 언젠가 또 놓친다. 사람도 뭉클이도 마찬가지다.** 그러니 처방은
"다음엔 조심하겠다"가 아니라 **디버깅용 재실행 경로 자체가 구조적으로 실제
발송에 못 닿게 만드는 것**이다.

**처방: 발송 함수 진입에 명시적 플래그를 요구한다.**

```
def send_briefing(..., confirm_send: bool = False):
    if not confirm_send:
        raise RuntimeError("dry-run 입니다. 실제 발송은 confirm_send=True 가 필요합니다")
    ...
```

크론이 정상 호출할 때는 `confirm_send=True`를 명시적으로 넘기고, **사람이나
뭉클이가 진단용으로 스크립트를 직접 건드릴 때는 기본값(`False`)이 막는다.**
"실행하면 나간다"가 아니라 **"내가 나가라고 분명히 말해야 나간다"**로 바꾼다.
이게 `#41`의 원칙("게이트는 구조로 막는다")이 몇 시간 만에 실전에 쓰인 자리다.
