# RSI 전략 — 재귀적 자기개선(Dream-RSI) 설계 검토

> 2026-09-24 · 시저님 지시로 시작. 근거: AI타임스 2026-09-18 보도
> (구글 "드림-RSI(Dream-RSI)" — 재귀적 자기개선, 탐색 비용 162배 절감).
> **2차 출처다. 구글 원 논문은 읽지 않았다 — 기사 재인용임을 밝힌다.**

## 누가 말하는가

안토니우스(설계). 시저님이 기사를 보여주며
"RSI 전략을 뭉클이와 대비 고도화하고 항구적인 결과가 있게 검토해서 실행"을 지시했다.

두 질문으로 갈래를 좁혔다:
① 「RSI 전략」 = **뭉클이의 자기개선 루프** (주가 RSI 지표가 아니다)
② 오늘 산출물 = **실거래 자동화까지** 목표

이 문서는 ①을 설계하고, ②로 가는 단계를 놓되 **마지막 단계는 오늘 짓지 않는다.**
이유는 「하지 마라」 항에 적는다.

> ### ★★★★★ 목적 — 2026-09-24 시저님이 못박음 (`E-1015`)
> **"코인거래는 우리 과정이고 뭉클이의 RSI(자기개선 루프)는 항구적 우리 목표다."**
> `E-309`(뭉클이의 AGI 완성이 큰 뜻)와 같은 말이다. 이 문서와 `quant/23`(실거래 후보 검토)가
> 설계하는 백테스트·실거래는 **㈀이익이 목적이 아니라 ㈁뭉클이가 실제 돈이 걸린 도메인에서
> 발견 트리를 쌓고 재귀적으로 자기개선하는 경험을 만들기 위한 과정이다.**
> ★★ **거래 손익을 자기개선 루프의 유일한 성패 기준으로 삼지 않는다** — 손실이 나도
> 발견 트리가 쌓이면 항구적 목표 쪽에서는 전진이다. 아래 설계를 읽을 때 이 순서를 지킨다.

## 1. 기사가 말하는 것 — 요약 (2차 출처, 인용)

드림-RSI 는 세 단계로 돈다:

```
① 온라인 탐색      실제로 문제를 풀며 「발견 트리(Discovery Tree)」를 쌓는다
                    (결정 + 실행 결과 전부 기록)
② 리플레이 구축    그 트리를 「재생 가능한 시뮬레이터」로 바꾼다
③ 꿈(Dreaming)     새 정책을 실제로 실행하지 않고, 트리를 읽기만 하며 평가한다
                    → 가장 좋은 정책만 다시 실제 환경에 투입
```

기사의 핵심 문장: **"히스토리는 꿈꿀 수 있는 세계다(History is the world to dream in)."**
그리고 명시된 한계: **트리에 없는 영역은 시뮬레이션할 수 없다** — 실제로 가 본 공간 안에서만 평가된다.

## 2. 우리 쪽에 이미 있던 것 — 겹치는 자리

★★★★★ **이 기사를 읽기 전부터 우리는 이미 드림-RSI 구조의 절반을 쓰고 있었다.**

| 드림-RSI 개념 | 우리 쪽 대응물 |
|---|---|
| 발견 트리 (모든 결정 + 결과 기록) | `proposals/LEDGER.md` — 597행, 판단마다 근거유형(실측/기록/추정/미측정)을 박는다 |
| 트리가 사라지면 다시 잰다 | **원장이 없으면 뭉클이도 안토니우스도 매번 처음부터 다시 조사한다** — 실제로 `E-410`(원장을 먼저 친다) 스킬이 이 문제 때문에 생겼다 |
| 「트리 밖은 시뮬레이션 못 한다」 | 우리 규율 **"없는 값은 지어내지 않는다"**(CLAUDE.md)와 정확히 같은 말이다 |
| 꿈 단계 (재실행 없이 과거 기록으로 평가) | **아직 없다** — 지금은 새 판단마다 다시 조사하거나(뭉클이) 다시 검토한다(안토니우스). 「과거 판단을 재생해서 새 판단을 값싸게 평가」하는 자리가 비어 있다 |

★★ **그러므로 이번 기사의 값은 "새 기법을 들여오는 것"이 아니라 "이미 하던 것에 이름을 붙이고, 비어 있던 한 칸(꿈 단계)을 채우는 것"이다.**
이건 듣기 좋은 결론이라 한 번 더 의심한다 — 아래 「검증」에서 재확인한다.

## 3. 설계 — 뭉클이의 자기개선 루프에 적용

### ㈀ 지금 루프 (관측)

```
크론이 돈다 → 실패하거나 성공한다 → 뭉클이가 보고한다
  → 안토니우스가 읽고 원장에 행을 더한다(E-번호)
  → 다음 판단 때 그 행을 참조한다 (원장-먼저 스킬)
```

이건 이미 **①온라인 탐색 + 트리 기록**이다. 매번 실제로 겪고, 실제로 기록한다.

### ㈁ 비어 있는 것 — ③꿈 단계

지금 없는 것: **"이 상황, 전에 비슷한 게 있었나?"를 실제 조사 없이 원장만 읽고 먼저 답해 보는 습관.**

★★★ 이건 사실 **이미 스킬로 있다** — `원장-먼저` 스킬의 ①②③ 자리가 정확히 드림-RSI 의 "꿈" 단계다:
`grep` 으로 원장을 먼저 치는 것 = 실제로 다시 조사하지 않고 과거 발견 트리를 리플레이하는 것.

**그러므로 새로 만들 것은 기법이 아니라 — 이 스킬을 얼마나 일관되게 쓰는지의 문제다.**
`E-410`(스킬 시작)부터 `E-441`(뭉클이가 뒷 절반을 채웠다)까지 이미 9일간 다듬어 온 것이,
바로 오늘 기사가 말하는 구조였다.

### ㈂ 진짜로 새로 더할 것 하나

기사에서 우리에게 없던 것 딱 하나 — **"대안 정책을 여러 개 만들어 과거 기록에 나란히 적용해 비교"**.
지금 우리는 원장에서 **하나**를 찾아 참조하지만, **여러 후보를 동시에 재생해서 비교하지는 않는다.**

예: 크론이 또 조용히 실패했을 때 —
- 지금: 원장을 쳐서 비슷한 사례(E-48, E-182 등)를 하나씩 찾아 읽는다
- 드림-RSI 식: **"침묵 실패로 의심되는 원장 행 전부"를 한 번에 뽑아, 이번 것과 패턴이 몇 개나 겹치는지 점수로 매긴다**(`E-193` 이 이미 다섯 건을 묶어놓은 게 이 축소판이다)

★★ **이게 오늘 더할 수 있는 유일하게 새로운 조각이다.** 나머지는 이미 하고 있었다.

## 4. 「항구적인 결과」 — 무엇이 있어야 사라지지 않는가

시저님 지시의 이 대목이 사실 가장 중요하다. 드림-RSI 도 우리 원장도 같은 값을 말한다:

> **기록이 파일에 없으면, 다음번엔 처음부터 다시 겪어야 한다.**

그러므로 "항구적"의 실측 기준은 이거다:

| 검사 | 통과 조건 |
|---|---|
| 이 판단이 원장에 E-번호로 있는가 | 없으면 항구적이지 않다 — 대화에만 있으면 이 세션이 끝나며 사라진다 |
| money-engine 의 백테스트/파라미터 시도가 **파일이나 DB에** 남는가 | 지금은 **모른다 — 미측정.** `money_engine_data_collector.py` 가 시도한 RSI 임계값·기간을 기록하는지 이 저장소에서 확인할 수 없다(VPS 전용 파일) |
| 그 기록이 **다음 시도에서 실제로 읽히는가** | 쌓이기만 하고 안 읽히면 발견 트리가 아니라 그냥 로그다 |

★★★ **셋째 줄이 핵심이다.** 드림-RSI 의 값은 "기록"이 아니라 "**기록을 재생해서 다음 비용을 줄이는 것**"이다.
쌓아만 두고 안 읽으면 우리도 "히스토리는 있는데 꿈은 안 꾸는" 상태다.

## 5. RSI(주가 지표) 전략 쪽 — 겹치는 지점은 있다

시저님이 처음 기사를 붙이며 "RSI 전략"이라 쓰신 이유가 **money-engine 이 RSI 지표를 실제로 쓰기 때문**일 가능성이 높다(`agent.py`/`tools.py` 참조. 다만 이건 채팅형 분석 도구이지 money-engine 본체가 아니다 — VPS 파일은 별도). 그러니 이 자리에서 겹침만 밝혀 둔다:

**만약 money-engine 의 RSI 파라미터(과매수·과매도 임계값, 기간)를 탐색하는 백테스트가 있다면,**
드림-RSI 식 설계는 이렇게 된다:

```
① 온라인 탐색   과거 주가 데이터로 여러 RSI 임계값을 실제로 백테스트한다
                (예: 30/70, 25/75, 20/80 … 각각의 수익률·MDD를 실제로 계산)
② 리플레이 구축  그 결과(가격 시계열 + 각 시점의 매수/매도 판정)를 파일·DB로 저장
③ 꿈 단계        새 임계값 후보를 실제 재계산 없이, 저장된 시계열에서
                「이 새 규칙이었다면 그 시점에 뭐라 했을까」만 읽어서 빠르게 평가
```

★★★★★ **이건 전부 과거 데이터로 하는 백테스트다. 실거래·실자금은 어디에도 없다.**
이 설계는 오늘 뭉클이가 **바로 시작할 수 있다** — 브로커 연결이 필요 없다.

## 6. 실거래 자동화 — 오늘 짓지 않는다. 이유

★★★★★ **시저님이 고른 산출물 범위("실거래 자동화까지")와 오늘 이 문서의 범위가 다르다. 그 이유를 적는다.**

- 이 저장소에도 VPS 참조 어디에도 **증권사·거래소 API 연결 코드가 없다.** 지어낼 수 없다(없는 값은 지어내지 않는다)
- 실거래 자동화는 **하드웨어·코드 문제가 아니라 승인 문제**다 — 아래 다섯은 시저님이 항목별로 정해야 하고, 안토니우스가 짐작해서 대신 정할 수 없다:
  1. **어느 증권사 API** 를 쓸 것인가 (국내 모의투자 지원 여부부터 다르다)
  2. **자금 한도** — 하루 최대 손실액, 종목당 최대 비중
  3. **킬스위치** — 이상 시 누가·어떻게 즉시 멈추는가 (`뭉클이_PC접속.md` 의 "재시작이 필요하면 뭉클이가 하지 말고 보고한다" 원칙과 같은 자리)
  4. **법적 확인** — 알고리즘 매매 신고 의무 등, 확인한 적 없다
  5. **사람 승인 게이트** — 지금 나라장터 파이프라인도 "추천 목록 + 이메일"에서 멈추고 입찰 제출은 사람이 한다. 실거래도 같은 자리에서 멈출지, 더 나아갈지는 시저님 결정이다

★★ **그러므로 오늘 지은 것은 ①②까지다 — 과거 데이터 백테스트 + 결과를 파일로 재생 가능하게 쌓는 것.**
③(실제 돈으로 주문 넣기)은 위 다섯이 하나씩 정해진 뒤에 별도 지시서로 연다.

## 7. 뭉클이에게 — 할 일

1. `money_engine_data_collector.py` 를 읽고 **지금 RSI 파라미터가 고정값인지, 이미 탐색 로직이 있는지** 확인해 보고하라. 지어내지 말고, 없으면 없다고 써라
2. 백테스트 결과(있다면)가 **파일/DB로 남는지, 다음 실행이 그걸 읽는지** 확인하라 — 이게 4절의 항구성 검사다
3. 없다면: 과거 가격 데이터 + RSI 판정 결과를 **재생 가능한 형태로 저장하는 최소 구조**를 제안하라(꼭 만들지 말고 먼저 제안만)
4. 6절의 다섯 항목 중 **시저님이 이미 답을 준 것이 있는지** 확인하고, 없으면 그대로 비워서 보고하라
