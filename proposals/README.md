# 사업계획서 생산 체계

정부지원사업 사업계획서를 **반복 가능한 공정**으로 만든다. 매번 백지에서 시작하지 않는다.

**이 문서는 작업 시작 전에 반드시 먼저 읽는다.** 아래 규칙은 협상 대상이 아니다.

---

## 왜 이렇게 하는가

심사에서 지는 이유는 문장력이 아니다. 이것이다.

> "AI 도입으로 업무 효율을 **30% 개선**하겠습니다"
>
> 심사위원: **"30%면 지금은 얼마인데?"**

답이 없으면 그 문장은 0점이다. 그리고 **"지금은 얼마인가"는 나중에 만들 수 없다.**
기준선은 사업 시작 전에만 측정된다.

그래서 이 체계의 중심은 글이 아니라 **원장(LEDGER.md)** 이다.

---

## 절대 규칙 6개

세어보라. 여섯 개다. 여섯 개라고 써놓고 다섯 개를 나열하지 않는다.

### 규칙 1 — 모든 문장은 근거 번호를 단다

계획서의 모든 주장 문장은 `LEDGER.md`의 행 하나를 가리켜야 한다.

```
잘못: 자사는 AI 자동화 운영 경험이 풍부하다.
맞음: 자사는 자동화 10종(크론 8·워크플로 2)을 상시 운영 중이다. [E-09]
```

**가리킬 번호가 없으면 그 문장은 쓰지 않고 지운다.** 근거를 만들어 붙이지 않는다.
근거가 필요하면 먼저 측정해서 원장에 행을 추가하고, 그다음에 문장을 쓴다.

### 규칙 2 — 없는 값은 지어내지 않는다

빈칸은 빈칸으로 둔다. 「미측정」「미정」「해당없음」으로 쓴다.

이건 우리 고집이 아니다. 공고가 직접 그렇게 하라고 쓴 경우가 많다.

> "타깃 AI 가속기가 정해지지 않은 기업도 신청 가능하며, 「미정」으로 기재하여도 **감점하지 않습니다**"
> "현재 수준을 측정한 적이 없는 경우 「미측정」으로 기재하여도 되며, **목표 수준만으로 평가**합니다"
> — 2026 온디바이스AI 공고 유형2 양식

**빈칸은 감점이 아니다. 허위기재는 선정 취소다.**

> "제출된 세부사업계획서 등의 허위, 위·변조, 그 밖에 부정하게 작성된 경우 **선정 취소 및 협약 해약**"

### 규칙 3 — 추정은 추정이라고 쓴다

원장의 근거유형이 `추정`인 행은 계획서 본문에서도 추정임을 밝힌다.
실측인 척하면 현장 확인에서 무너진다. 밝히고 쓰면 오히려 신뢰가 올라간다.

```
맞음: 도입 후 연 1,200만원 절감이 예상된다(추정, 산출근거 [E-14]).
```

### 규칙 4 — 배점표 없이 초안을 쓰지 않는다

공고마다 배점이 다르고, 같은 공고 안에서도 유형별로 다르다.
**먼저 `00_공고해부.md`를 채운다.** 배점을 모르는 채로 쓴 글은 어디에 힘을 줄지 모르고 쓴 글이다.

배점표를 못 구했으면 **못 구했다고 보고하고 멈춘다.** 짐작으로 채우지 않는다.

### 규칙 5 — 원문을 봤는지 밝힌다

공고 원문 PDF/HWP를 직접 읽은 것과, 요약본·기사·검색 결과로 안 것은 다르다.
후자면 **"원문 미확인, 2차 정보 기준"** 이라고 표시한다.

자격 요건과 마감 시각은 **반드시 원문으로 확인한다.** 2차 정보로 판단해서 자격 미달로 떨어지면
그건 글을 못 써서 떨어진 게 아니다.

### 규칙 6 — 제출 전 `QUALITY_GATE.md` 전 항목을 통과한다

한 항목이라도 걸리면 제출하지 않는다. 게이트를 낮추지 않는다.

## 디렉터리 구조

```
proposals/
├── README.md                    ← 지금 이 문서. 매번 먼저 읽는다
├── LEDGER.md                    ← 근거 원장. 단일 진실 원천
├── QUALITY_GATE.md              ← 제출 전 검사 항목
├── TEMPLATE_공고해부.md          ← 새 공고가 오면 이걸 복사해서 시작
└── <마감일>_<공고약칭>/
    ├── 00_공고해부.md            ← 배점표 → 항목별 목표 점수 → 필요 근거
    ├── 01_초안.md                ← 본문. 문장마다 [E-번호]
    ├── 02_제출점검.md            ← QUALITY_GATE 실행 결과
    └── 원문/                     ← 공고 PDF·양식 HWP 원본 그대로
```

폴더 이름은 **마감일을 앞에 둔다.** 정렬하면 급한 순서가 된다.

---

## 작업 순서

새 공고가 들어오면 이 순서로만 진행한다. 단계를 건너뛰지 않는다.

| 단계 | 하는 일 | 끝났다고 말할 조건 |
|---|---|---|
| **1. 자격** | 신청 자격·제외 대상·마감 **시각**을 원문에서 확인 | 자격 판정이 「가능/불가/확인필요」 중 하나로 확정 |
| **2. 해부** | 배점표를 `00_공고해부.md`에 옮기고 항목별 현재 예상 점수를 매김 | 배점 합이 공고와 일치 |
| **3. 결손** | 점수가 낮은 항목에 어떤 근거가 없는지 목록화 | 각 결손이 「측정 가능 / 불가」로 분류됨 |
| **4. 측정** | 측정 가능한 결손을 실제로 재서 `LEDGER.md`에 행 추가 | 새 E-번호가 원장에 있음 |
| **5. 초안** | 문장마다 `[E-번호]`를 달아 작성 | 번호 없는 주장 문장이 0개 |
| **6. 게이트** | `QUALITY_GATE.md` 전 항목 실행 | 전 항목 통과 |
| **7. 제출** | 마감 **이틀 전** 제출 | 접수 확인 회신 수령 |

**마감 당일에 제출하지 않는다.** 마감 시각이 자정이 아닌 경우가 많다
(예: 18:00, 16:00). 서버도 몰린다.

---

## 보고 규칙

작업 결과를 보고할 때 **직접 실행해서 본 것**과 **추정·기억**을 반드시 구분해 표시한다.

```
실행해서 본 것: 공고 원문 7쪽 전문 추출. 유형2 배점 100 + 가산 5 확인.
추정: 우리 예상 점수 72점 — 평가위원 성향을 모르므로 추정이다.
확인 못 한 것: 작년 선정기업 목록. 공개돼 있지 않음.
```

"확인 완료"라고 쓰기 전에 스스로 묻는다. **내가 실제로 열어봤는가, 그럴 것 같다고 생각했는가.**

설정 파일에 값이 적혀 있는 것은 그 값이 동작한다는 증명이 아니다.
