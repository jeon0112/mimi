# 근거 원장

**단일 진실 원천.** 계획서의 모든 주장 문장은 여기 한 행을 가리킨다.
가리킬 행이 없는 문장은 쓰지 않는다.

## 근거유형

| 표기 | 뜻 | 계획서에서 |
|---|---|---|
| `실측` | 직접 재서 숫자를 얻은 것 | 그대로 쓴다 |
| `기록` | 커밋·로그·DB·문서에 남아 있는 것 | 그대로 쓰되 출처를 밝힌다 |
| `추정` | 근거 있는 산정 | **반드시 "추정"이라고 밝힌다** |
| `미측정` | 아직 재지 않은 것 | 쓰지 않는다. 재고 나서 쓴다 |

## 행 추가 규칙

1. **번호는 재사용하지 않는다.** 폐기하는 행은 지우지 말고 `상태: 폐기`로 표시하고 사유를 남긴다.
   계획서 초안이 이미 그 번호를 가리키고 있을 수 있다.
2. **측정시점을 반드시 적는다.** 6개월 전 숫자와 어제 숫자는 다른 무게다.
3. **출처는 다시 찾아갈 수 있게 적는다.** "내부 자료"는 출처가 아니다.
   커밋 해시, 파일 경로, 실행 ID, 문서번호를 적는다.
4. **수치가 없는 행은 만들지 않는다.** "경험이 풍부하다"는 근거가 아니다.


**하나의 숫자로 적지 않는다.** 모르는 것을 아는 척하면 그 표가 통째로 못 믿을 것이 된다.

**이 사례가 원장에 주는 것**
- 앞의 세 건은 *자동화가 조용히 멈춘* 경우였고, 이건 *인증이 조용히 끊긴* 경우다. 유형이 다르다.
- 그리고 **사람이 말을 걸기 전까지 아무도 몰랐다.** 헬스체크는 초록불이었다.
  `Up` 은 프로세스가 살아 있다는 뜻이지 일을 하고 있다는 뜻이 아니다.
- → E-16(아래)의 근거가 된다.

**E-17 상세 — 여섯 번째 사례, 그리고 가장 미묘한 형태 (2026-09-06)**

메인 모델을 `glm-4.6` → `glm-5.3` 으로 바꿨다. 그것만 바꿨다.
그런데 **압축 임계값이 함께 3.4배로 올라갔다.**

```
glm-4.6   ctx   204,800  < 512K → 75% → 임계 153,600
glm-5.3   ctx 1,048,576  ≥ 512K → 50% → 임계 524,288
오늘 최대       265,365  <  524,288  →  압축이 한 번도 안 걸림
```

컨텍스트 창이 큰 모델은 "50%에서 압축해도 여유가 있다"는 설계다. 코드는 맞게 동작했다.
**바뀐 것은 모델 하나인데, 함께 움직인 값이 있었고 아무도 그걸 몰랐다.**

| | |
|---|---|
| 겉보기 | 대화 정상 · 응답 정상 · 오류 0건 |
| 실제 | 26만 토큰 컨텍스트를 **258회** 반복 전송 (캐시읽기 68,371,008 ÷ 265,365) |
| 입력 / 출력 | **554배** |

**이 사례가 앞의 다섯과 다른 점 — 로그조차 안 남는다.**

앞의 다섯은 최소한 흔적이 있었다. 0건 메일, drift_skip 기록, 실행 시각, 401 응답.
이건 **조건이 안 맞으면 로그 라인 자체가 안 찍힌다.**
`Preflight compression` 은 `should_compress` 가 True 일 때만 기록되므로,
"압축이 안 걸렸다"는 사실을 알리는 로그가 존재하지 않는다.

> **안 일어난 일은 로그에 안 남는다.** 침묵 실패의 가장 다루기 어려운 형태다.

**진단 과정에서 우리가 틀린 것도 함께 남긴다.**
같은 날 두 가지를 바꿨다(메인 모델, compression 슬롯 모델). 시간 상관만 보고
뒤엣것(compression 슬롯)을 지목했으나, 코드를 읽어보니 트리거 판정은
`self.threshold_tokens` 와 `self.context_length` 만 보고 이 둘은 **메인 모델**의
컨텍스트 창에서 파생한다. 슬롯 모델은 요약 실행 단계에서만 쓰인다.
**시간 상관은 착시였다.** 코드가 아니라 시계를 근거로 삼으면 이렇게 틀린다.

**덧 — 고쳤다는 사실조차 로그로는 확인되지 않는다 (2026-09-06 17:32)**

캡 153,600 을 적용하고 검증하려 했으나 **기동 로그에 임계값이 찍히지 않는다.**
`context_compressor.py` 2370행 `if not getattr(self, "_log_init_summary", False): return`,
3386행 `self._log_init_summary = not quiet_mode`. 게이트웨이는 quiet_mode 로 도므로
초기화 요약은 **설계상** 출력되지 않는다. 과거 로그 전체에서도 이 라인은 0회였다.

그래서 같은 로더·같은 클래스로 직접 만들어 값을 읽었다.

```
config threshold_tokens = 153600 (int)
context_length          = 1,000,000
유효 threshold_tokens   =   153,600      ← 524,288 이 아니다
```

E-17 이 "압축이 안 걸린 사실이 로그에 안 남는다"였다면, 이건 한 겹 더 안쪽이다.
**고친 값이 들어갔는지조차 로그로는 알 수 없다.** 관측은 코드를 직접 돌려서 얻었다.

| 항목 | 상태 |
|---|---|
| config.yaml 42행 반영 · 백업 생성 | 확인 |
| 재시작 후 새 프로세스에 로드 | 확인 (17:32 재기동) |
| 유효 임계값 153,600 | 실측 (컴프레서 직접 생성 재현) |
| 기동 로그 출력 | 안 찍힘 (quiet_mode, 설계상) |
| config → 컴프레서 배선 | 확인 (`agent_init.py` 2269 → 2790) |
| 실전 `Preflight compression` 발동 | **미확인** — 컨텍스트가 아직 문턱 미달 |

**"발동 안 함"과 "설정 안 먹음"은 이 시점에 구분되지 않는다.** 그래서 적용됨이라고 쓰지 않는다.

**배선 확인 (2026-09-06)** — 재현은 손으로 캡을 넣어 만든 것이라 "클램프가 동작한다"는
증명이었지 "게이트웨이가 그 값을 넘긴다"는 증명이 아니었다. 코드로 확인했다.

```
config.yaml  compression.threshold_tokens: 153600
  → agent_init.py 1799  load_config_readonly()
  → agent_init.py 2269  compression_threshold_tokens = int(...)
  → agent_init.py 2790  ContextCompressor(threshold_tokens_cap=...)
  → context_compressor.py 3177  min(cap, context_length) < threshold → 클램프
```

**E-21 (지뢰) — 이 수정은 없는 설정에 기대어 서 있다.**

2774행 `ContextCompressor(...)` 는 `if _selected_engine is not None: ... else:` 의
**else 브랜치**다. 플러그인 엔진이 선택되면 2763행 `update_model` 경로로 가고
**그쪽은 `threshold_tokens_cap` 을 넘기지 않는다.**

지금 이 갈림길이 안전한 이유는 단 하나 — `config.yaml` 에 `context:` 섹션이 **없어서**
기본값 `"compressor"` 가 쓰이기 때문이다. 즉 **누군가 나중에 `context.engine` 을
플러그인으로 설정하면, 임계값은 아무 오류 없이 524,288 로 돌아간다.**
설정을 지우지도 않았는데 고친 것이 사라진다. 로그도 안 남는다.

→ `context.engine` 을 건드릴 때는 반드시 유효 임계값을 다시 잰다. 이 문장이 그 알람이다.

**E-24 상세 — 여덟 번째 사례, 그리고 고치자 드러난 것 (2026-09-07)**

KOSPI 지표가 전부 NaN 이었다. 처음 설명은 "일요일이라 휴장"이었다.

**고친 감시에 날짜 경계 지뢰가 있었다 (E-50)**

E-48 을 고치면서 「로그 마지막 줄이 **오늘(UTC)** 것인가」로 판정하게 했다.

```
크론 실행   09-10  21:00 UTC  →  로그 줄 "2026-09-10 21:00"
감시 확인   09-11  05:00 UTC  →  "오늘" = 2026-09-11
                                 로그는 09-10  →  NO_RUN   ← 거짓 경보
```

**21:00 UTC 는 KST 로 다음날 06:00 이다.**
크론이 도는 날짜와 감시가 보는 날짜가 **항상 다르다.**
정상으로 돌아도 매일 아침 오탐이 뜬다.

E-05(요일을 UTC 로 판단해 「일요일 휴장」)의 재현이고,
E-45(거짓 경보는 진짜 경보를 죽인다)와 만난다.

→ **날짜를 세지 말고 시간을 재라.**

```
✗  마지막 줄이 「오늘」 것인가      ← 자정·시간대에 걸린다
✓  마지막 줄이 26시간 이내인가     ← 경계가 없다
```

26 = 주기 24 + 여유 2. 하루를 건너뛰면 26을 넘으니 그건 잡힌다.
**「오늘/어제」를 세지 않으면 자정도 시간대도 상관없어진다.**

★ **고친 것에도 시험이 필요하다.**
  뭉클이의 시험 A·B·C 는 옳았으나 **날짜가 바뀌는 경우**를 넣지 않았다.
  세 갈래를 다 통과해도 네 번째 갈래가 남아 있을 수 있다.

**감시 장치가 첫 실전에서 속았다 (E-48)**

2026-09-09 에 우리는 「실패를 어떻게 아는가」를 만들었다.
로그에 `EXIT=0` 만 적지 말고 **CSV 마지막 날짜를 함께 적게** 했다. 그건 옳았다.

**그런데 그 로그가 갱신됐는지는 안 봤다.**

```
21:01 크론 실행 → 스크립트를 못 찾아 아무것도 안 씀
06:37 옛 줄이 그대로 「마지막 줄」로 남음
감시가 그 줄을 읽음 → EXIT=0 → "정상"  ← 거짓 정상
```

→ **「최신 값」을 봤는데 그것이 최신이 아니었다.**
   새 줄이 없으면 **옛 줄이 최신이 된다.**

★ 그래서 감시의 원칙이 하나 바뀐다 —
  **감시는 「나쁜 값」이 아니라 「값이 없음」을 찾아야 한다.**
  나쁜 값은 있으면 보인다. **값이 안 생긴 것은 안 보인다.**
  그런데 실패의 대부분이 그것이다 (E-17 — *안 일어난 일은 로그에 안 남는다*).

```
✗  로그 마지막 줄이 EXIT=0 인가
✓  로그 마지막 줄이 **오늘 것인가**      ← 아니면 안 돈 것이다
```

E-31(낡은 값이 정상처럼 보인다)의 재현이자, 한 걸음 더 나간 형태다.
**낡은 것이 「최신」 자리에 앉아 있으면 낡은 줄도 모른다.**

**손으로 돌린 것과 크론이 돌린 것은 실행 경로가 다르다 (E-49)**

어제 수동 시운전은 **성공했다.** 그래서 크론을 걸었다.
그런데 크론은 `script` 필드를 다른 방식으로 실행했고,
거기 shebang 줄이 명령어로 붙어 있어 **경로 자체가 틀렸다.**

안토니우스는 어제 *"오늘 손으로 되는 것과 내일 크론이 돌아서 되는 것은 다르다"* 고
적어두었다. **맞는 말이었으나 왜 다른지는 몰랐다.**
이제 안다 — **실행 경로가 다르다.**

→ **「손으로 됐다」는 「크론으로 된다」의 증거가 아니다.**
   증거는 **크론이 한 번 돌고 난 뒤의 새 줄**뿐이다.

**쉬운 시험은 통과한다 (E-46 · E-47)**

같은 엔진을 두 가지 시험에 걸었다.

| 시험 | 겹침 | 판정 |
|---|---:|---|
| **다른** 두 사람 (병 vs 정 · 신약 vs 신강) | **3.3%** | 통과 |
| **비슷한** 두 사람 (같은 일간 · 같은 강약) | **41 ~ 72%** | **실패** |

재료가 다르면 결과가 다른 건 당연하다. **그건 시험이 아니라 확인이다.**
갈리는 자리는 **재료가 비슷할 때**다.

→ **시험은 통과할 만한 곳이 아니라 갈릴 만한 곳에 놓는다.**

★ 원인: **명식은 여덟 글자인데 서사는 한 글자(일간)만 읽었다.**
  일간은 10개뿐이다. 서사가 일간으로 결정되면 **세상 사람이 10종류가 된다.**
  그것이 「수많은 사주앱」의 정체다.

**겹침을 목표로 삼으면 속는다 (2026-09-09 설계 판단)**

E-46 을 고치는 길은 「다시 쓰기」인데, **여기에 함정이 있다.**

```
LLM 에게 다시 쓰게 하면 겹침은 쉽게 내려간다. 표현만 바꾸면 된다.
측정은 통과하는데 실제로는 나아지지 않는다.
```

실제로 재봤다 — 같은 뜻을 다른 말로 쓰기만 해도 **겹침 100% → 0%, 통과.**

그래서 반대편에서 한 번 더 재는 지표를 만들었다 — **재료 인용률**
(`report_composer.material_citation`).
**그 사람의 고유한 값**(오행 수치·4주 간지·현재 대운)이 본문에 나오는가.

| | 포러 겹침 | 재료 인용 |
|---|---|---|
| 템플릿 그대로 | 100% (실패) | 0% (실패) |
| **표현만 바꿈** | **0% (통과)** ← 속는다 | **0% (실패)** ← 안 속는다 |
| 재료를 읽음 | 0% (통과) | 100% (통과) |

→ **겹침을 목표로 삼지 말고 재료 인용을 목표로 삼는다. 겹침은 결과다.**
   재료를 읽으면 겹침은 저절로 내려간다.

★ 임계값은 **아직 걸지 않았다.** 재본 뒤에 정한다.
  근거 없이 숫자를 박으면 그 숫자가 어디서 왔는지 아무도 모르게 된다 (E-22).

| E-43 | `_EVIDENCE_TERMS` 에 손금 어휘는 촘촘한데 **사주 어휘가 거의 없었다.** `일간`·`명식`·`신강`·`대운`이 빠져 있었다 → 근거를 단 문장이 「근거 없음」으로 세어졌다 |

**자가 짧으면 물건이 길어 보인다.**
자를 안 고치고 리포트를 고쳤으면, **좋은 문장을 나쁜 자에 맞춰 깎았을 것이다.**

→ **숫자가 나쁘게 나오면 물건을 고치기 전에 자를 먼저 본다.**

★ 그리고 **거짓 경보는 진짜 경보를 죽인다.**
  매번 8건이 뜨면 사람은 경고를 안 본다.

**여섯 번째 — 만들어 뒀는데 부르는 것이 없다 (E-42 · E-44)**

|---|---|---|

**돈을 쓰면서 아무 일도 안 일어난 것**이다.

**E-26 — 소비는 자동화하고 생산은 잊는다**

E-24 에서 "CSV 가 열흘 멈췄다"까지 왔다. 원인을 찾으니 멈춘 것이 아니었다.

```
CSV 를 읽는 코드   9개 · 그중 여러 개가 크론으로 매일 돈다
CSV 를 쓰는 코드   1개 (data_fetcher.py)
그것을 부르는 크론  0개          ← 애초에 없었다
CSV 수정시각        전부 2026-08-31 09:01  (그날 한 번 손으로 돌린 것)
```

**고장이 아니라 부재다.** 그리고 이 형태가 발견하기 어려운 이유는,
**소비 쪽이 다 자동화되어 있어서 시스템 전체가 도는 것처럼 보이기 때문이다.**
매일 분석이 나오고 매일 메일이 온다. 그 재료가 열흘 전 것이라는 사실만 안 보인다.

E-25(미구현 스텁)와 같은 계열이다 — **망가진 것이 아니라 처음부터 없었던 것.**
"왜 멈췄나"를 묻기 전에 **"애초에 누가 돌리기로 되어 있었나"** 를 물어야 한다.

**E-25 — 미구현이 "데이터 없음"으로 위장한다**

펀딩비가 5일 전부 null 이었다. 거래소 두 곳 모두라서 수집 실패로 보였다.
코드를 열어보니 호출 자체가 없었다. 주석이 스스로 말하고 있었다 —
*"실제로는 API 호출 필요, 여기서는 '데이터 없음'으로 처리"*.

**두 곳 다 null 인 이유는 두 곳 어디도 호출한 적이 없어서였다.**
`null` 이 "못 가져왔다"와 "안 가져온다"를 덮는다.

→ 스텁은 `null` 이 아니라 **`NOT_IMPLEMENTED` 로 표시한다.** 그래야 구분된다.

**E-22 — 게이트는 인용되면서 낮아진다**

`paper_trading_server.py` 45행은 `max_trades = 400` 이다. 그런데 보고서를 쓰던
스크립트가 *"실전 제안 최소 요건: 30건"* 을 하드코딩했고, 그 파일이 두 번 복사되며
세 곳으로 퍼졌다. 코드는 400 을 지키는데 **사람이 읽는 문장이 30 이 되었다.**

→ 그 숫자를 다시 쓰지 않는다. **`max_trades` 를 참조한다.**
   같은 값을 두 곳에 적으면 언젠가 반드시 갈라진다.
