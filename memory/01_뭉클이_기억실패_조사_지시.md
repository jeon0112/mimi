# 뭉클이 지시 — 기억 저장 실패 조사

> 2026-09-09 · 안토니우스 작성 · 시저님 승인 후 전달
> 배경: 2026-09-08 메모리 저장이 **4회 연속 실패**했다.
> 사유는 "용량 초과", 그리고 "정리 시도도 실패".
> 뭉클이는 *"되는 것처럼 쓰지 않습니다 — 현재 기억에는 없습니다"* 라고 정직하게 보고했다.
> **그 보고가 이 조사의 출발점이다.** 숨겼다면 우리는 지금도 몰랐을 것이다.

---

## 왜 이것이 그래프보다 먼저인가

그래프는 **기억을 담을 그릇**이다.
그릇을 만들기 전에, 지금 담기지 않는 이유를 알아야 한다.

오늘 배운 규율이 저장되지 않으면 내일의 뭉클이는 모른다.
`CLAUDE.md` 와 `AGI로_가는_여정` 에는 남았지만,
그건 **읽으러 가야 아는 것**이지 몸에 밴 것이 아니다.

---

## 이 조사의 계율

```
읽기만 한다. 지우지도, 늘리지도, 다시 시도하지도 않는다.
```

이번에도 **「고장이 아니라 부재」**일 수 있다.
E-25(펀딩비 — 호출한 적이 없다) · E-26(CSV — 돌린 적이 없다) ·
E-27(Neo4j — 붙은 적이 없다) 과 같은 모양이다.

**"왜 안 되나" 앞에 "원래 되기로 되어 있었나"를 먼저 묻는다.**

---

```
[뭉클이 — 기억 저장 실패 조사]

■ 누가 말하는가
  안토니우스(설계)가 쓰고 시저님이 승인한 지시다.

■ 성격
  조사다. 수리가 아니다. 읽기만 해라.

■ 하지 말 것 (먼저 읽어라)
  · 기억 항목을 삭제하지 마라
  · 상한값을 늘려서 통과시키지 마라
  · 저장을 재시도해서 덮지 마라
  · 설정 파일을 고치지 마라
  숫자만 가져와라. 무엇을 버릴지는 시저님이 정하신다.

■ 답할 것 — 네 가지

  1) "용량 초과"의 용량은 무엇의 용량인가
     디스크인가 / 항목 수 상한인가 / DB 파일 크기인가 / 임베딩 인덱스인가.
     넷 중 무엇인지 모르겠으면 "모르겠다"고 써라.
     ★ "가득 찼다"는 진단이 아니다. 숫자로 확인해라.
       예: df -h 의 해당 마운트, DB 파일 바이트 수, 항목 수, 설정된 상한

  2) 지금 몇 건이고 상한은 얼마인가
     현재 항목 수 = ?
     상한 = ?        (상한이 코드/설정 어디에 적혀 있는지 파일·행까지)
     상한이 어디에도 없으면 "없다"고 써라. 그것도 답이다.

  3) "정리 시도도 실패"의 사유 원문
     요약하지 말고 로그 원문 그대로 가져와라.
     로그가 남지 않았으면 "로그 없음"이라고 써라.
     ★ 지어내지 마라. 기억으로 복원하지 마라.

  4) 오래된 항목을 버리는 규칙이 애초에 있었는가
     · 있다  → 어디에 있고 언제 마지막으로 돌았나 (크론/스케줄러 이름과 마지막 실행 시각)
     · 없다  → **그것이 원인이다.** 고장난 게 아니라 만든 적이 없는 것이다.
     ※ E-26 때 CSV 갱신 크론이 0개였던 것과 같은 확인 방식이다.

  5) 지금 저장된 것들이 「경험」인가 「절차」인가
     최근 항목 20건만 제목/요약 수준으로 나열해라. (전문은 필요 없다)
     각 건 옆에 한 글자로 표시해라 —
       경 = 겪어서 알게 된 것 (예: "그 기관은 서류를 두 번 요구한다")
       절 = 반복해서 따를 절차·규율 (예: "막히면 우회로를 찾지 않는다")
       문 = 사람이 쓴 문서를 그대로 옮겨둔 것
     ★ 판단이 애매하면 "애매"라고 써라. 억지로 나누지 마라.

■ 보고 형식
  네 항목을 번호 그대로. 각 항목에 명령어와 그 출력을 함께 붙여라.
  확인 못 한 것은 "확인 못 함"이라고 써라. 추정을 확인처럼 쓰지 마라.

■ 막히면
  권한이 없거나 파일이 안 보이면 **"제 권한 밖입니다"라고 써라.**
  다른 자격증명을 찾거나 권한을 넓혀서 우회하지 마라.
  "못 한다"는 실패가 아니라 정확한 보고다.
```

## 조사 뒤에 정할 것 (지금 정하지 않는다)

숫자가 오면 갈림길이 나뉜다.

| 원인 | 다음 수 |
|---|---|
| 상한이 있는데 정리 규칙이 없다 | **버리는 규칙을 만든다.** 무엇을 버릴지는 시저님이 정하신다 |
| 상한 자체가 없다 (디스크였다) | 저장소를 옮기거나 그래프로 이관한다 |
| 정리 코드가 있는데 깨졌다 | 그때 비로소 수리다 |
| 애초에 저장 경로가 없었다 | E-28 로 원장에 올린다 |
| **「절」이 「경」보다 많다** | **서랍이 틀린 것이다.** 아래 참조 |

**어느 쪽이든 상한을 올려서 넘기는 것은 답이 아니다.**
그건 다음 4회 실패를 뒤로 미루는 것뿐이다.

## 5번 질문을 왜 넣었나 (2026-09-09 추가)

시저님이 가져오신 「AI 네이티브 SDLC」 문서가 지식을 넷으로 나눈다.

| 유형 | 무엇을 담나 |
|---|---|
| **Memory** | 에이전트가 **겪어서** 알게 된 것 |
| **Skills** | 반복해서 따르는 **절차** |
| **RAG** | **사람이 쓴 문서** |
| **MCP** | 외부 실시간 접근 |

여기서 어제 내가 쓴 문장을 다시 본다 —
*"오늘 배운 **규율**이 저장되지 않으면 내일의 뭉클이는 모른다."*

**규율은 Memory 가 아니다. Skills 다.**
「막히면 우회로를 찾지 않는다」·「없는 값은 지어내지 않는다」는
뭉클이가 겪어서 안 것이 아니라 **반복 실행할 절차**다.

그렇다면 4회 실패의 원인이 이것일 수 있다:

```
고장이 아니라, 부재도 아니라 — 잘못된 서랍이다.
절차를 경험 서랍에 쌓아서 경험 서랍이 넘쳤다.
```

E-25·26·27(「고장이 아니라 부재」)의 **네 번째 변종**이다.
맞다면 상한을 올려도 낫지 않는다. **옮겨야 낫는다.**

그래도 5번은 여전히 **조사**다. 옮기지 마라. 세기만 해라.
